# 自习室预约系统

> AI 智能问答 · 协同过滤算法推荐 · 地图 API 与自习室位置 · 二维码签到 · 预约时段冲突校验 · 积分激励 · 预约提醒 · ECharts 运营数据统计

起因挺实在：朋友在图书馆自习室做过一段时间管理，最头疼的不是座位不够，而是**座位说不清到底谁在用**。早上七点有人拿本书占座，人一整天没来；有人来了发现位置被占，只能站在走廊里翻手机查哪个教室有空；值班老师想统计"这层楼今天到底坐了多少人"，只能一圈一圈走过去数。

这套系统就是冲着这个场景做的：**把自习室的类型、座位、可预约时段、预约记录、签到、积分全部落到平台上，学生自己在手机上就能看空位、约时段、扫码进场**。做毕设答辩时，"两个预约的时段怎么算冲突"和"签到为什么必须是扫码而不是点按钮"这两段特别有讲头，比单纯写增删改查扎实。

## 一、项目简介

自习室预约管理系统采用前后端分离的 B/S 架构，由用户前台和管理员后台组成。系统以用户账号、自习室类型、自习室、座位、预约配置、预约记录、通知公告、消息通知、积分记录、轮播封面、系统标签、AI 会话与消息记录等为主要业务数据，围绕"用户注册登录、浏览自习室、智能推荐、选择座位或整间自习室、预约时段校验、确认预约、二维码签到、积分记录、通知提醒、数据统计与后台维护"的自习室使用场景组织功能。用户可查看自习室信息与可预约时段，完成散座或整间预约，查询预约记录、积分和公告，并通过 AI 助手获取自习室相关问答；管理员可维护用户、自习室类型、自习室、座位和预约配置，处理预约记录与逾期记录，发布公告和消息，并查看座位预约、预约状态及积分记录统计。

## 五、核心实现

### 5.1 用户注册登录、JWT 认证与端侧划分

系统将账号划分为用户和管理员两类角色。用户在用户端完成自习室浏览、预约、签到、积分查询和个人信息管理；管理员在管理端维护用户、自习室类型、自习室、座位、预约配置、公告与轮播封面，并处理预约记录与逾期记录。登录时用户需要选择身份角色并填写图形验证码，服务端校验通过后签发 JWT，令牌中写入用户 ID 与角色；请求拦截器解析令牌后将当前用户保存到线程上下文，前端路由守卫根据角色把用户导向前台、把管理员导向运营工作台。数据范围的约束同样落在服务端——接口需要的当前用户直接取自线程上下文，而不是由前端传参指定。

### 5.2 自习室类型、自习室与座位的三层建模

系统的空间资源采用三层结构：自习室类型 → 自习室 → 座位。自习室类型用于归类（如静音自习室、研讨自习室、考研专座），自习室保存名称、封面、位置、开放时间、座位总数、标签与状态，座位按自习室关联并保存座位号、座位类型和当前状态。预约配置则以自习室为单位维护可预约时段、单次最长时长、是否允许整间预约等规则。三层分开的好处是：**时段规则挂在自习室上、座位明细挂在座位上**，同一间自习室调整开放时间不用逐个改座位，新增座位也不用重复配置规则。

### 5.3 预约配置、时段冲突校验与两种预约方式

用户在前台选择自习室与日期后，页面按可预约时段展示空闲情况，支持散座预约（精确到具体座位）和整间预约（占用该自习室全部座位）两种方式。提交时系统创建预约记录，保存用户、自习室、座位、日期、起止时间、预约方式、状态和预约编号。

时段校验的关键在于**判断区间重叠，而不是比对开始时间是否相同**。两个预约冲突的充分必要条件是"已有预约的开始时间早于新预约的结束时间，且已有预约的结束时间晚于新预约的开始时间"；只判断开始时间相等，会把 9:00–11:00 和 10:00–12:00 这种明显冲突的组合放过去。整间预约与散座预约共享同一套校验：创建整间预约时要检查该自习室在重叠时段内是否存在任何散座预约，创建散座预约时也要检查是否落在某个整间预约占用的时段里。取消或逾期的预约不参与冲突计算，对应时段立即释放，可以被后续用户预约。

### 5.4 二维码签到、签退与学习时长统计

每条预约在创建成功后生成专属签到二维码，二维码由服务端按预约编号签发，前端使用 qrcode 渲染展示。用户到达自习室后扫码签到，服务端校验二维码归属的预约、当前时间是否落在预约时段内、以及该预约是否已经签到过，校验通过后写入签到时间并把预约状态推进到使用中。学习结束时扫码签退，记录签退时间。

这里有个刻意的设计：**签到不能做成页面上的一个按钮**。按钮意味着"人在宿舍也能点已到达"，签到就失去了核验作用；由扫码触发、服务端核验时段，签到时间才是有约束的。签到与签退的时间点分别落库之后，累计学习时长、学习天数、日均学习时长和连续学习天数都由这些记录计算得出，个人中心还会按年度呈现学习热力图与周学习时长统计，供用户自己回看学习节奏。

### 5.5 基于历史预约的协同过滤推荐

自习室推荐采用协同过滤思路，以历史预约记录为依据。系统先取出当前用户预约过的自习室集合，再找出同样预约过这些自习室的其他用户，最后取这批用户预约过的其他自习室作为候选，按共同偏好的重合程度排序后返回。这样得到的结果是"和你学习习惯相近的人还常去哪些自习室"，而不是简单地按总预约量排列。

新用户没有历史记录，推荐会回退为按预约热度取自习室列表，保证首屏不出现空白。推荐接口的返回结构里带上推荐理由所用的自习室名称，前端可以顺带说明"因为你预约过 XX 自习室"，推荐从黑盒变成可解释的一句话。

### 5.6 AI 智能问答与会话记录

用户端提供 AI 助手页面，围绕自习室开放时间、位置、座位情况、预约规则、积分规则等问题进行问答。系统调用 DeepSeek 接口，并在请求中拼入自习室、座位与预约配置等业务数据作为上下文，让模型基于真实数据作答，避免编造不存在的自习室名称或开放时间。AI 会话与消息记录分别落库：会话保存用户与标题，消息保存角色、内容与时间，用户可查看历史会话并继续追问。**落库的是完整回答而不是流式片段**，否则翻历史时会出现半截话。

### 5.7 积分激励与积分流水

积分用于引导用户按时到场、按约使用。预约签到、按时签退、完成一段学习会按规则增加积分，爽约或逾期未签到则按规则扣减积分。每次积分变动都会写入一条积分记录，保存变动类型、变动值、变动后余额、关联预约与发生时间，用户在个人中心可查看积分明细。

积分余额的处理方式是**以流水为准，而不是单独维护一个计数器字段**。计数器在并发、重复提交、任务重跑等情况下都可能与实际流水对不上，而且一旦对不上就无法自动恢复；每次变动写一条记录、余额由该用户积分记录累计得出，数量永远等于明细之和，也天然具备可追溯性。

### 5.8 预约提醒：定时任务、站内通知与邮件

系统通过定时任务扫描即将开始的预约，对满足提醒条件的记录生成通知：站内通知写入消息通知表，用户登录后在消息中心看到未读数量并逐条或批量已读；同时按用户邮箱发送提醒邮件，减少"约了但忘了来"的情况，这也是逾期记录和爽约的主要来源。

提醒环节有个容易被忽略但要处理的点：**提醒必须带发送标记**。定时任务按固定周期运行，如果只判断"是否临近开始时间"就直接发通知，同一批预约会被反复提醒好几次，用户收到的不是提醒而是骚扰。写入通知的同时记录该条预约的提醒状态，已提醒的不再重复发送。

### 5.9 自习室位置与地图服务

自习室在基础信息中维护位置描述与经纬度，前台提供自习室位置页面，通过地图 API 呈现自习室分布，并支持查看单个自习室的位置与周边信息。用户可以先在地图上按距离挑自习室，再进入该自习室查看时段与座位，把"去哪自习"和"约哪个位置"合成一条顺畅的路径，也避免只看到自习室名称却不知道具体在哪个楼栋。

### 5.10 ECharts 运营数据统计与自习室使用流程

管理端提供座位利用率、预约状态分布和积分记录三类统计图表。座位利用率按"已预约时段数 ÷ 该自习室可预约时段数"计算，可下钻到单个自习室与具体日期，用于判断哪些时段紧张、哪些座位长期闲置；预约状态分布统计各状态预约的占比，反映取消与逾期的整体情况；积分记录统计呈现积分变动的类型构成与趋势。前端使用 ECharts 渲染，便于管理员调整开放时段与座位配置。

系统以用户注册登录为起点，用户浏览自习室列表与位置、参考智能推荐确定目标，选择散座或整间方式并完成时段冲突校验后提交预约；预约成功后生成签到二维码，用户在预约时段内扫码签到、结束时扫码签退，签到与签退记录汇总为学习时长与热力图；积分按规则随预约与签到情况变动并写入流水；即将开始的预约通过站内通知与邮件提前提醒，逾期未到的预约进入逾期记录；管理员维护自习室、座位与预约配置，处理预约与逾期记录，并通过运营统计图表掌握整体使用情况。

## 八、适合谁

- 想做**场景贴切、故事好讲**的毕设：自习室预约方向，答辩时从"早上七点去占座"讲起，评委自己就有校园经历，一听就懂
- 想体现**配置化建模**能力的同学：自习室类型、自习室、座位、预约配置四层挂靠，规则与明细分开维护，论文里能画一张清楚的结构图
- 想在论文里写**业务校验规则**的同学：预约时段冲突的区间重叠判断、整间与散座互斥、取消即时释放，是可以单独成节的算法说明
- 需要**算法落点**的同学：基于历史预约的协同过滤推荐，含候选集构造、排序与冷启动回退，比"热门榜单"更能撑起一节
- 想写**二维码与核销**逻辑的同学：服务端签发签到码、扫码校验归属与时段、签到签退双向留痕，是一条完整可讲的核销链路
- 想在论文里写**大模型应用**的同学：把自习室、座位与预约规则作为上下文喂给模型，AI 问答结果与会话记录一并落库
- 想体现**数据统计**能力的同学：座位利用率、预约状态分布、积分记录三类图表加学习时长热力图，数据来源清楚、口径统一
